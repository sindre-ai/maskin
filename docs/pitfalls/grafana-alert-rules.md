# A Grafana Alert Rule That Imports Cleanly and Then Says Nothing Useful

- **What**: Grafana's *unified alerting* schema (`apiVersion: 1`, rules carrying `data[].model.expr`, `condition`, `noDataState`) looks close enough to Prometheus rule format to be edited as if it were one. Three traps follow, none of which surfaces until the alert fires during the incident it was written for:
  1. **`$value` is not a number.** In Prometheus/Alertmanager templating `$value` is the float. In Grafana alerting it is the rule's **ValueString** — a string like `[ var='headroom' labels={…} value=0.18 ]`. So `{{ humanizePercentage $value }}` does not print `18%`; it errors or emits garbage into the notification body. The correct form names the query refId: `{{ humanizePercentage $values.headroom.Value }}`.
  2. **`noDataState: NoData` is not a substitute for an `up` alert.** The `DatasourceNoData` instance Grafana synthesises carries **none of the rule's labels** — no `instance`, no `name`, no `$values` — so a carefully written summary renders as `": SeaweedFS  has  of its disk free."`, an empty-bodied page naming a condition that is not the one that fired. It also fires *every* rule over that datasource at once, so one unreachable target pages several times at several severities, and it cannot distinguish "scrape gap" from "never scraped at all" — which is the state every new scrape target is in until its first successful scrape.
  3. **`promtool check rules` cannot validate these files.** It validates the *Prometheus* rule schema; pointed at a unified-alerting file it rejects the whole thing and tells you nothing about the PromQL inside. So the natural CI reflex ("run promtool over the alerts dir") produces either a hard failure that gets deleted, or, if the file is skipped, no coverage at all.
- **When to check**: Any time you add or edit a file under `observability/*/alerts/`, or any Grafana alert rule defined as YAML rather than in the UI.
- **Fix pattern**: Use `$values.<refId>.Value` in every annotation, never bare `$value`. Give target-down its **own rule** on `up{job="…"} == 0` and let the metric-derived rules clear on no data (`noDataState: OK`) — a rule that states its condition beats a synthesised instance that cannot. To validate in CI, extract `data[].model.expr`, substitute the `${…}` deployment placeholders, and feed *that* to promtool as a synthetic rules file; check the structural invariants (condition names a real refId, `__expr__` nodes reference real refIds, uids unique across files) separately. `observability/validate-alerts.py` does exactly this and is wired into CI's `observability-config` job — extend it rather than writing a second validator.
- **History**: All three found in review of PR #1483, which added `observability/coolify-host/alerts/seaweedfs-disk.yaml`. Both rules used bare `$value`; `up{job="seaweedfs"}` was cited five times across the config, env example and README as the safety net for a down target and was never alerted on, with `noDataState: NoData` documented as covering it. Fixed in the review commit by correcting the templates, adding a `SeaweedFS volume server unreachable` rule, flipping the two disk rules to `noDataState: OK`, and adding the validator plus its CI job — the config had had no syntax gate of any kind, since the existing `alloy validate` step is hardcoded to the agent-server path.
