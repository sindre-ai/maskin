# An OAuth Scope Requested in Code but Not Declared in the Provider's App Manifest

- **What**: The scopes an integration *requests* (`auth.config.scopes` and `extraAuthParams.user_scope` in `apps/dev/src/lib/integrations/providers/<name>/config.ts`) and the scopes the provider-side app *declares* (for Slack, `docs/integrations/slack/manifest.yml`, pasted into the Slack app) are two halves of one contract. Asking for a single scope the app does not declare makes the provider reject the **entire** authorize with `invalid_scope` — not just that scope. So a one-word addition to a config array can take *connecting the integration* down completely, for every workspace, while every test and type-check passes. The reverse drift is quieter but also real: the manifest can declare scopes the code never requests, which reads as "we have this permission" when no token actually carries it. Slack additionally splits some scopes over time — the blanket `search:read` became `search:read.public` / `.private` / `.mpim` / `.im` / `.files` / `.users` — so a plausible-looking scope name copied from an old doc or from model memory is not necessarily a scope that still exists.
- **When to check**: Any time you add, rename or remove an entry in a provider config's `scopes` array or `extraAuthParams.user_scope`. Also whenever you copy a scope name from documentation rather than from the app manifest — verify it against the provider's *current* reference, since scope names get split and deprecated.
- **Fix pattern**: Treat the app manifest as the authority for what may be requested, and assert the subset relationship in a test so the two files cannot drift silently — `apps/dev/src/__tests__/lib/integrations/providers/slack.test.ts` (`requests only scopes the Slack app manifest declares`) parses `manifest.yml`'s `bot:` / `user:` lists and fails if `config.ts` asks for anything absent from them. When you add a scope to the config, add it to the manifest in the same commit and re-apply the manifest to the provider-side app before the code ships. Remember that existing installs keep their old token either way — `lib/integrations/scope-drift.ts` surfaces that as a Reconnect prompt, but somebody still has to reconnect.
- **History**: Found 2026-09-01 while widening the Slack MCP tool surface from one tool (`slack_send_message`) to thirteen. The work initially requested `search:read` as the user scope, taken from Slack's `search.messages` reference page; `manifest.yml` had in fact long declared the granular `search:read.public` / `.private` / `.mpim` / `.im` set, and requesting the retired blanket name would have failed every Slack authorize with `invalid_scope`. The same review found `config.ts` requesting four bot scopes (`files:read`, `commands`, `links:read`, `links:write`, `team:read`) that the manifest did not declare — pre-existing drift in the other direction that had gone unnoticed because nothing compared the two. Fixed by switching to the granular scopes, reconciling the manifest, and adding the subset assertion.
