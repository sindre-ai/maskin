# The Remote Completion Path Skipped Classification and Failover Entirely

- **What**: `session-manager.ts` has two completion paths for the same lifecycle. `handleCompletion()` (local Docker) reads the in-memory `stdoutTail`, runs `classifyCreditExhaustion`, writes `result.failure_reason`, and calls `maybeRetryClaudeOAuthOnNextSlot`. `markRemoteSessionComplete()` — the path taken by every session dispatched to an `agent_servers` row, which is how sessions run in production — did none of it: it wrote `{ exit_code }` and returned. The visible symptom is a session that simply "fails" when its Claude subscription hits a usage limit, with no reason recorded and no swap, *no matter how many subscriptions are connected* — because nothing ever called the code that walks the chain. Two things hide it: the local path works perfectly in dev (so it demos fine and every mocked-DB unit test of `handleCompletion` passes), and the missing step is invisible in the remote method's own body — you only see it by diffing the two paths side by side. It also masquerades as a detection bug: the classifier and the slot chain were both correct and fully tested, and the failure looks exactly like "we don't recognise Claude's error codes".
- **When to check**: Any time you add a step to `handleCompletion()`, and any time a lifecycle has both a local (Docker/in-process) and a remote (HTTP-dispatched) implementation. Ask of every step in the local path: does the remote path do this too? Note that a remote session has **no in-memory `stdoutTail` buffer** — its stdout reaches `session_logs` over HTTP — so any step reading that buffer needs a DB-backed equivalent (`readSessionStdoutTail`) rather than a copy-paste.
- **Fix pattern**: Mirror the step in `markRemoteSessionComplete`, reading the tail from `session_logs` and keeping it stdout-only so both paths classify from the same material. Make any pre-CAS DB read best-effort (try/catch): `stopSession()` calls this method after the sandbox is already dead, so a throw becomes a spurious "stop failed" 400 for a stop that succeeded. Cover it with an **integration** test — the mocked-DB unit tests enumerate `db.select()` calls positionally, so they detect that you added a query but can never show the row transition or the retry session. Confirm the test fails with the fix reverted; the reverted assertion output (`{ exit_code: 1 }` with no `failure_reason`) is exactly what production was writing.
- **History**: Reported 2026-09-04 as "sessions just fail because they run out of tokens even though there is a backup", with a screenshot of session `9870f874…` (`host.microsandbox.internal`, so remote) failing on `You've hit your limit · resets 2:30pm (UTC)` alongside a `rate_limit_event` envelope carrying `"rateLimitType":"five_hour"`. Every layer checked out in isolation — the banner was in `CLI_BANNERS`, `claudeRuntimeFailoverReason` mapped it to `quota_exhausted_5h`, the slot chain was correct — which is what made it look like a detection gap. Third instance of the local/remote path divergence class, after the interactive seed turn (above) and the dropped exit code in `docs/runbooks/agent-session-failures-2026-08-11.md`. Fixed on `claude/llm-error-classification-failover` (PR #1533).
