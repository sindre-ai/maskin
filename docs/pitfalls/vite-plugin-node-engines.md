# A Build Plugin Whose Transitive Dep Outranks the Builder's Node Version

- **What**: A plugin imported at the **top level** of `apps/web/vite.config.ts` is loaded on every build, no matter what gating you put around its *use* further down. If any transitive dependency declares an `engines.node` higher than the builder's Node, the config file fails to load and **every** build dies — including the production image — with an error from deep inside the dependency that names neither the plugin nor the version constraint. It is easy to miss locally because developer machines run newer Node than CI and the Docker base image do: the same command passes on Node 22 and fails on Node 20, so "I ran `pnpm build`" is not evidence unless it ran on the builder's version.
- **When to check**: Any time you add a plugin to `vite.config.ts` (or any build config). Check the new package's transitive `engines.node` against `.github/workflows/ci.yml` (`node-version: 20`) and `apps/dev/Dockerfile` (`FROM node:20-alpine`) — not against `node -v` on your machine.
- **Fix pattern**: If the plugin is optional — only needed when some credential or flag is present — import it **lazily inside the gate** with a dynamic `await import()`, using vite's async config form (`defineConfig(async () => ({ ... }))`). A build without the credentials then never loads it. Pair that with an explicit Node-version assertion in the gated branch so enabling the feature on an unsupported builder fails with a sentence that names the constraint, instead of a cryptic stack trace from the transitive dep.
- **History**: PR #1484 added `@grafana/faro-rollup-plugin` as a top-level import in `apps/web/vite.config.ts` for Faro source-map upload. It pulls `@grafana/faro-bundlers-shared` → `undici@^8.1.0`, and undici 8 declares `engines.node >= 22.19.0`. Every CI `pnpm build` failed with `TypeError: webidl.util.markAsUncloneable is not a function` from `undici/lib/web/cache/cachestorage.js`, and the production Docker build (`FROM node:20-alpine`) would have failed the same way — the branch could not have deployed. Not caught before push because the authoring machine was on Node 22.19.0. Fixed by moving the import behind the existing `uploadConfigured` gate as a dynamic import.
