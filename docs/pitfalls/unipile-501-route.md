# A Provider Route That Exists in the API but Not for the Provider You Called It With (501)

- **What**: Unipile's v2 API is multi-provider, so several endpoints exist in the reference but are only implemented for *some* providers. Called with LinkedIn, they answer `501 { type: 'api/not_implemented', detail: 'Use <other> endpoint for this provider.' }` — the route is real, the path is valid, the credentials are fine, and the fix is named in the response body that nobody reads because the status is a 5xx. Two of these have now bitten, both on the messaging surface, both the same pair: the generic route (`/v2/{account}/chats`, `/v2/{account}/chats/send`) versus the inbox-scoped one (`/v2/{account}/inboxes/{inbox_id}/chats`, `/v2/{account}/inboxes/{inbox_id}/chats/send`). LinkedIn has an inbox concept, so it only implements the inbox-scoped forms. Two things make it hard to see: the classifier in `providers/linkedin-unipile/errors.ts` swept `status >= 500` into `LINKEDIN_UNAVAILABLE`, which is **retryable**, so a permanently-wrong URL burned three backoff attempts and then surfaced as a LinkedIn outage; and the in-process mock (`__mocks__/unipile-server.ts`) answered `200` on the generic route, so the whole suite was green against a path production could never call.
- **When to check**: Any time you add or edit a Unipile v2 call in `providers/linkedin-unipile/unipile-client.ts`, and any time you copy a path from a Unipile reference page — check whether an inbox-scoped or otherwise provider-scoped variant of that endpoint exists, and prefer it for LinkedIn. Also suspect this immediately whenever one operation on an integration fails while its siblings work (here: new threads failed, replies into existing threads worked).
- **Fix pattern**: Use the inbox-scoped route with `DEFAULT_LINKEDIN_INBOX` (`CLASSIC_PRIMARY`) as the default, the way `listConversations` and `sendMessage` both now do. Make the mock serve the **wrong** route the way the live API serves it — a 501 envelope — so a regression fails the suite instead of passing it. Assert the exact path against `mock.inbox()` (see `client.test.ts` → `read-surface routes` / `write-surface routes`); every LinkedIn bug found in live testing so far has been a wrong path, not wrong logic. And keep 501 out of the retryable 5xx bucket: it is classified as `INVALID_INPUT` ("the request was wrong"), not `LINKEDIN_UNAVAILABLE`.
- **History**: First hit on `listConversations` (bare `/chats` → 501 "Use List inbox Chats endpoint"), fixed 2026-09-04 with a comment on the call site — but the identical bug in `sendMessage` on the send path was not looked for, so `linkedin_send_message` could never open a new conversation while `linkedin_reply` worked fine. Surfaced 2026-09-08 by an agent that read the error as "LinkedIn is unavailable / there is no start-a-chat tool" and escalated to a human. Fixed by routing `sendMessage` through `/v2/{account_id}/inboxes/{inbox_id}/chats/send` ("Start a Chat from Inbox"), reclassifying 501/`api/not_implemented` as `INVALID_INPUT`, and making the mock 501 the bare route.
