# A "Healthy" Collector Component That Silently Matches Nothing

- **What**: Grafana Alloy components report `state: healthy` based on whether they *evaluated*, not on whether they produced anything. Three distinct instances of this are now on record, all with the same shape — the config is accepted, `alloy validate` passes, the service is green, and every query written against it returns empty:
  1. **`job` set as a static label loses to the component's own value.** `loki.source.journal` stamps `job="loki.source.journal.<id>"` and `prometheus.exporter.unix` stamps `job="integrations/unix"` onto their own output. `prometheus.scrape`'s `job_name` only fills targets that have *no* `job`, so setting it there is inert. Logs are genuinely ingested; they are just under a `job` value nothing selects.
  2. **`discovery.docker` returns zero targets because of an unrelated network.** Docker SD computes network labels for *every* network on the daemon before returning any container, so one malformed IPAM gateway anywhere aborts discovery for everything. An IPv6-enabled network whose gateway is stored as a CIDR (`fd00:…::1/64`) rather than a bare address is rejected by `netip.ParseAddr`; Docker accepts such a value at creation time, so it can sit there indefinitely. The component stays healthy; the log pipeline ships nothing.
  3. **Unbounded values used as labels.** Container name as a Loki label on a Coolify host mints a new stream per deploy (`app-<projectId>-<deployId>`), so the index grows with deploy count and `{service_name="app"}` matches nothing.
- **When to check**: Any change to an Alloy config, or a first install on a new host. Never conclude a pipeline works because the service is running and the config validated.
- **Fix pattern**: Always set `job` in a **relabel rule placed downstream of the component**, never as a static label — and note that "in a relabel rule" is not sufficient on its own. A rule only beats the component's own labelling if it runs *after* it: `loki.relabel` wired as a source's `relabel_rules` (or as a later stage in the `forward_to` chain) relabels the **entries** a component emits and wins, whereas `discovery.relabel` relabels the **target list** a source consumes and therefore runs before it and loses. `prometheus.scrape`'s `job_name` loses for a third reason — it only fills targets that carry no `job` at all. Always derive log stream identity from a **stable** attribute (`com.docker.compose.service`, not the container name). And **verify by query, not by status**: run the documented LogQL/PromQL selector and confirm it returns rows, and check `journalctl -u alloy | grep -iE "unable to refresh|error"` for components that are healthy but empty. See `apps/agent-server/observability/alloy.alloy` and `observability/coolify-host/alloy.alloy`, where each of these is commented at the site it applies.
- **History**: (1) found and fixed during the initial agent-server rollout, 2026-08-26. (2) found 2026-08-27 while adding the Coolify host config; remediation requires recreating the offending Docker network, which restarts the containers on it — see `observability/coolify-host/README.md` → "Docker log discovery can fail silently on an IPv6-enabled network". (3) designed out before first deploy of the Coolify host config.
