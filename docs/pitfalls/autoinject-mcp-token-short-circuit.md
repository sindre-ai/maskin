# Auto-Inject MCP Registered but Never Reaches a Session (Token Resolution Short-Circuit)

- **What**: `mcp.autoInject: true` on a provider's `config.ts` records the intent that every workspace with an active integration for that provider gets `mcp.server` attached to every session's `MCP_SERVERS_JSON`. That intent is not evidence anything happens. The path that *acts* on it lives in `apps/dev/src/services/session-manager.ts`'s `buildLaunchSpec`, and before **P3-F** its non-GitHub branch called `tokenManager.getValidToken(...)` for every active integration BEFORE the `autoInject && server` check. When a provider stores no per-provider access token — linkedin-unipile's credential blob is `{ account_id }` with no `accessToken`, so its Standard OAuth2 branch throws `Integration <id> has no access token` — the shared catch logged a plausible-looking `Failed to load credentials for linkedin-unipile` and the autoInject branch never ran. The result: sessions in a workspace with LinkedIn connected shipped with zero LinkedIn tools, and agents fell back to whatever else was on the session (in the 2026-09-11 incident, Unipile's own v1 docs-explorer connector, which produced every `503 no_client_session` on record). Nothing failed loudly — the intent was recorded, the OAuth handshake completed, `GET /api/integrations/providers` still reported `autoInject: true`. Only the class of test that drives the full session-manager path with the provider's real credential shape could see the gap. A config-shape unit test on the provider's `mcp` block passed the whole way through.
- **When to check**: Any time you add a new provider with `mcp.autoInject: true`, and any time you edit `SessionManager.buildLaunchSpec`'s active-integrations loop. Also whenever a provider is added whose MCP server template authenticates on Maskin credentials (e.g. `Authorization: Bearer ${MASKIN_API_KEY}`) rather than the provider's own envKey — those providers are the failure mode: token-manager may throw for reasons that don't matter to the server's actual auth path.
- **Fix pattern**: `apps/dev/src/__tests__/lib/integrations/providers.contract.test.ts` iterates `listProviders()`, and for every provider with `mcp.autoInject && mcp.server` drives `SessionManager.startSession` with a realistic credential blob for that provider (OAuth token for slack/posthog, `{ account_id }` for linkedin-unipile), then asserts `MCP_SERVERS_JSON.mcpServers['integration-<provider>']` equals the provider's declared `mcp.server` verbatim AND that `logger.warn('Failed to load credentials for <provider>')` does not fire. Add a new autoInject provider to the registry and the contract test's provider list expands automatically; a new autoInject provider whose credential shape breaks the class fix will fail this test in CI. Runtime fix in `session-manager.ts`: check whether the server spec actually references the provider's envKey (`serverSpecReferencesEnvKey` in `apps/dev/src/lib/integrations/mcp-server-spec-refs.ts`) — if not, a token failure is fine and auto-inject proceeds anyway.
- **History**: Introduced when linkedin-unipile's `mcp.autoInject: true` shipped in PR #1595 without any test exercising the session-manager path (PR #1595's tests pinned the config shape only). Manifested 2026-09-11 as `503 no_client_session` failures across the Sales Rep loop, IR loop, and Copywriter loop; RCA on 2026-09-12 traced it to the token-resolution short-circuit. Runtime fix in **P3-F** ([PR #1608](https://github.com/sindre-ai/maskin/pull/1608)); class-fix contract test added in **P3-D** (rescoped).
