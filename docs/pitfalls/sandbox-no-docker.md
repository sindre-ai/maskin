# Agent Sandbox Sessions Can't Run `docker-compose` — Use `pnpm dev:no-docker`

- **What**: Agent sessions working on this repo run inside an ephemeral sandbox (a microsandbox/`msb` microVM, per `apps/agent-server/src/services/microsandbox.ts`) with no `docker.sock`, no `DOCKER_HOST`, and no privileged mode — `docker-compose up` (which `pnpm dev` / `pnpm dev:win` depend on for Postgres + SeaweedFS) always fails inside that sandbox. There is no error suggesting a fix; it just fails the way any missing-Docker environment would, and CI is the only place local E2E/integration specs are known to run for a PR authored from inside such a session.
- **When to check**: Any time an agent session needs a live Postgres + S3-compatible stack for local verification (integration tests per `.claude/rules/verification.md`, manual UI checks, E2E specs) and `pnpm dev`/`pnpm dev:win` fails because Docker isn't available.
- **Fix pattern**: Run `pnpm dev:no-docker` instead. It calls `scripts/bootstrap-local-devstack.sh`, which vendors a portable Postgres 16 build and the SeaweedFS `weed` binary and runs both as plain unprivileged processes — no Docker, no `apt-get`, no root. (Postgres's own binary dynamically links `libxml2`, which pulls in ICU; the script vendors those three `.so` files the same way, from `snapshot.debian.org`'s permanent content-addressed archive, so nothing is installed system-wide.) Everything is cached under `$MASKIN_DEVSTACK_DIR` (default `~/.cache/maskin-devstack`) and the whole thing is idempotent — safe to re-run. Call `bash scripts/bootstrap-local-devstack.sh` directly if you only need the DB/S3 up (e.g. for `pnpm test:integration`) without the full dev server. With no Docker socket (the normal case in a sandbox) `scripts/dev-no-docker.sh` runs `scripts/lib/docker-absent-guard.sh` first: it prints `no Docker socket at <path>`, sets `MASKIN_DOCKER_UNAVAILABLE=1` so `apps/dev` skips the agent-base image warm-up, and carries on — the API still boots and answers `/api/health`. Set `MASKIN_REQUIRE_DOCKER=1` to make a missing socket a fast non-zero exit instead. Only a `unix://` (or unset) `DOCKER_HOST` is tested as a socket path; a `tcp://` or `http://` one means a remote daemon and leaves the warm-up on. The local Postgres cluster is initialised UTF8 (`initdb --encoding=UTF8 --locale=C`); a cluster bootstrapped by an older version is SQL_ASCII and the script stops on it — recreate it with `rm -rf "$MASKIN_DEVSTACK_DIR/pgdata"` and re-run the script (this drops local data and re-applies every migration). SeaweedFS's master wants port 9333 (and 19333), and agent sandboxes already use 9333 for the browser proxy, so a busy master port is expected there, not an error: the script moves to the next free port, prints one warning naming the holder when it can see it, and records the choice as `S3_MASTER_PORT` in `$MASKIN_DEVSTACK_DIR/env.sh` (and `weed.master.port` beside it). Set `S3_MASTER_PORT=<port>` to pick one yourself. Nothing else in the repo reads that port, since S3 clients only need `S3_ENDPOINT`. In a sandbox, also set `MASKIN_DEV_EXTERNAL=1` before starting the web dev server: Vite only binds `0.0.0.0` and accepts the mapped host name (`host.microsandbox.internal`) under that flag, and otherwise blocks it as an unknown host.
- **History**: Diagnosed on `bet/foryou-brief-feed` (2026-08-13) when a PR's own description noted local E2E "could not be run in this sandbox" — traced to `container-manager.ts` creating session containers with `NetworkMode: 'bridge'` and no Docker socket bind. `scripts/bootstrap-local-devstack.sh` / `scripts/dev-no-docker.sh` added instead of granting sessions a Docker socket (larger attack surface) or baking Postgres/SeaweedFS into `docker/agent-base`'s image (forces every session to carry the weight even when it never touches the DB).
