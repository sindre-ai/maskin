# A Per-Provider Cleanup That Matches Every Credential of a Multi-Identity Provider

- **What**: `detachProviderMcpServers` (`apps/dev/src/lib/integrations/mcp-detach.ts`) strips a provider's MCP entry from every agent when an integration is disconnected, matching on the URL prefix `/api/integrations/<provider>/mcp`. That is right for a provider with one endpoint. LinkedIn serves **one endpoint per identity** — `/mcp/{instanceSlug}`, `instanceSlug = linkedin-{unipileAccSlug}-{identitySlug}` — and every one of those URLs starts with the same prefix. So disconnecting one person's LinkedIn removed every identity's entry from every agent in the workspace, including the identities that were still connected. Nothing errors and nothing tells a human: the agents simply boot without the tools, and the failure surfaces days later as a business symptom ("outbound is frozen"). Reconnecting does not repair it, because detach is deliberately one-way (`Reconnecting does NOT re-attach`). A second trap made it durable: agents cannot repair it themselves. Changing another actor's `tools` needs a human admin or owner (`routes/actors.ts`), and the per-identity entry is built only in the web app (`buildLinkedInIdentityPreset`), so an agent has neither the permission nor the shape.
- **When to check**: Any cleanup, sync or reconciliation that matches agent config (`actors.tools.mcpServers`) by URL or name, for a provider whose `identityFanout` is `per-identity` or `per-installation` (LinkedIn today; GitHub's per-installation entries are the next candidate). Also any new code that runs on disconnect, revoke or reconnect and touches more than the one credential row it was called for. Ask: if the workspace has two credentials for this provider and one is disconnected, what happens to the other's entries?
- **Fix pattern**: Each provider declares how its entries on an agent are recognised in its own `config.ts` (`mcp.server`, or `mcp.entry` for `per-identity` / `per-installation` providers), and `apps/dev/src/lib/integrations/mcp-entries.ts` applies that for every provider — no per-provider list in the detach code or the route. Only the disconnected credential's entries go: LinkedIn matches the slugs its `unipileAccSlug` owns (longest prefix wins, so `linkedin-magnus-` does not swallow `linkedin-magnus-noeddegaard-personal`), GitHub matches the `GITHUB_TOKEN_<OWNER>` variable of its installation, and a provider with one shared entry (Slack serves a single `/api/integrations/slack/mcp` however many teams are connected) keeps it until the last active connection goes. Entries on an external URL are matched on the url and the provider's token variable together, so a hand-written server on the same url with its own key survives. When in doubt the entry is kept: a dead entry is the safer miss than deleting a live one. Cover it with a real-Postgres test of two credentials and several agents (`apps/dev/src/__tests__/integration/integrations-mcp-detach.test.ts`) and keep `mcp-entries.contract.test.ts` green: it fails when a provider declares an MCP surface the matcher cannot recognise. The earlier tests only used the aggregate URL shape and passed throughout. Not yet built, tracked in the PR: a human-approved attach card so an agent can ask for a lost entry back, and a one-click restore on reconnect that reads the `mcp_servers_detached` list already recorded on the `events` row.
- **History**: Found 2026-10-20. Disconnecting Magnus's LinkedIn at 14:22 UTC on 2026-10-14 removed `linkedin-krumhausen-personal` from seven agents that still had a live connection (events 887485 to 887494), freezing outbound sales for six days. The `events` log shows the same wipe for the old aggregate entry on 2026-09-10, 09-11 and 09-12. The first guess was the provider's own `disconnect.ts` (`preDisconnect`, which only deletes the Unipile account); the cause was found by listing every writer of `actors.tools` and then confirmed from the audit events, not from the code. Fixed in PR #2227.
