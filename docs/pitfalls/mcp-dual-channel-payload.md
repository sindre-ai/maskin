# An MCP Tool Whose Two Response Channels Carry Different Payloads

- **What**: Every MCP tool response has two channels — `content[0].text` and `structuredContent` — and `packages/mcp/src/response-cap.ts` states the invariant plainly: *"content now carries the same full-JSON payload as structuredContent."* When a tool diverges, the caller sees one payload that has visibly fewer fields than the other and reasonably concludes the response was **truncated or tampered with**, not that it is a summary card beside its source. The failure is entirely in the model's reading of a well-formed response, so nothing errors, nothing is logged, and no test catches it — the tool "works". A weaker model then escalates: it reports a degraded tool, refuses to act, and asks the human to fix an infrastructure problem that does not exist. Two things make it worse: a **description that promises the richer shape** (`get_actor` advertised "returns the full record including `system_prompt`, `skills`…" in snake_case while delivering a camelCased `heroCard` subset), and the absence of a **read→write pointer** — a read tool whose description names no counterpart leaves a model that has just read a record with nothing in context telling it the write tool exists, so it enumerates tools from memory and gets it wrong.
- **When to check**: Any time you add or edit a tool in `packages/mcp/src/server.ts` that returns both `content` and `structuredContent`, and any time you add a `heroCard` (or other presentation projection) to a tool's response. Also check that the `tools.ts` description names the fields the caller will actually receive, under the casing they will actually arrive in.
- **Fix pattern**: Return the full record **alongside** the card under its own key, mirroring `list_workspaces`' `{ heroCard, workspaces }` — not `{ heroCard }` alone. Assert it with a test that parses `content[0].text` and `expect(...).toEqual(structuredContent.<recordKey>)`, which fails the moment the channels drift. Write descriptions that state the shape as delivered and say explicitly that a card and a record are the same data. End every read tool's description with its write counterpart ("This tool is read-only — to change any of these fields, use `update_actor`").
- **History**: `get_actor` returned `content` = the full snake_case record (plus `setup`, `url`) but `structuredContent` = `{ heroCard }` only — the sole tool in its family to drop the record. On 2026-08-31 a Chief of Staff agent in the Mesh Firm workspace (session `3a7a8bc9`, running on the fallback `deepseek-v4-flash` route because the workspace has no `claude_oauth` credentials) read two agents, judged the responses "degraded/truncated", additionally misread Claude Code's client-side TodoWrite system-reminder as a prompt injection carried in the tool output, claimed `update_actor` did not exist (it was in the session's `init` tool list all along), and stopped to ask the human for a capability it already had. Fixed by adding `actor` to `structuredContent`, rewriting the `get_actor` description to match the delivered shape and name `update_actor`, and — separately — redacting `billing`/`llm_keys`/`claude_oauth`/`custom_llm.api_key` from the workspace rows `list_workspaces`/`create_workspace`/`update_workspace` return, which had been shipping Stripe ids and live provider API keys into every agent's context.
